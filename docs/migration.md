# データ移行とロールバック

Issue #92 / Epic #81。VeloX が保存する永続データ (設定・履歴・ブックマーク・
入力履歴・サイト権限・セッション) の**版管理・移行・バックアップ・壊れたデータの
退避・ロールバック**の仕組みと、構造を変えるときの開発手順をまとめる。設計判断の
記録は [decisions/archive.md](decisions/archive.md) の **D164**、リリース運用
(Stable 昇格条件・ロールバック方針) は [release-channels.md](release-channels.md)
を参照。

実装は `src/browser/migration.rs` (汎用の仕組み) と
`src/browser/persistence.rs` (各ストアの版と接続)。

## 1. 対象ファイル

データの保存先は [user-guide.md](user-guide.md) の「アンインストール」節の表
(`VELOX_DATA_DIR` が設定されていればそこ)。

| ファイル | 現在の版 | 版の定数 |
| --- | --- | --- |
| `settings.json` | 1 | `browser::settings::SETTINGS_SCHEMA_VERSION` |
| `history.json` / `bookmarks.json` / `input_history.json` / `session.json` / `site_permissions.json` | 1 | `browser::persistence::STORE_SCHEMA_VERSION` |
| 拡張機能の索引・ストレージ (`extensions/`) | 1 | 各モジュールの `*_SCHEMA_VERSION` (D163。原子的書き込み・`.corrupt` 退避・版の検査を既に持つので本書の仕組みには載せていない) |

## 2. 約束 (起動時にファイルを読むとき)

| 状況 | 動作 | 残るファイル |
| --- | --- | --- |
| ファイルが無い | 既定値で起動 | — |
| 現在の版 | そのまま読む | — |
| `schema_version` 欄が無い (Issue #92 以前の VeloX が書いたもの) | **現在の版として読む** (既存プロファイルはそのまま使える) | — |
| 古い版 | **移行前に元のバイト列を控え**、1 版ずつ移行して読む | `<name>.v<旧版>.bak` |
| 古い版で移行に失敗 | 既定値で起動。元データは控えに残る (控えが書けなければ元ファイルを退避) | `<name>.v<旧版>.bak` |
| 自分より新しい版 (新版からダウングレードした) | **写しを取ってから**読めるだけ読む。読めなければ自分の版の控え (更新時に取られたもの) を使う。どちらも駄目なら既定値 | `<name>.v<新版>.bak` |
| JSON として壊れている・形が違う・`schema_version` が整数でない | 退避して既定値で起動 (**起動不能にしない**) | `<name>.corrupt-<unixミリ秒>` (ファイルごとに直近 3 件) |
| 読み出し自体に失敗 (権限・ロックなど) | 既定値で起動。一時的な可能性があるので退避はしない | — |
| 書き込み途中で落ちた一時ファイル (`<name>.tmp`) | 読まずに削除 | — |

平常時以外の出来事は stderr に `velox: <file>: ...` の 1 行で残る。

保存は常に**原子的** (同じディレクトリの一時ファイルへ書いて `sync` → `rename`)
で、トップレベルに `"schema_version": N` を付ける。電源断などで保存が中断しても
ファイルは「前の内容」か「新しい内容」のどちらかになる。

## 3. ロールバック (利用者向け手順)

### 3.1 新版から旧版へ戻す

1. VeloX を終了し、旧版を入れ直す ([release-channels.md](release-channels.md) §6)。
2. 旧版を起動する。旧版が #92 以降のものなら、新版が書いたファイルは
   `<name>.v<新版>.bak` へ自動で写され、読める範囲 (追加フィールドだけの
   変更なら全部) はそのまま使われる。構造変更で読めない場合は、新版へ更新した
   ときに取られた `<name>.v<旧版>.bak` (更新直前の状態) が自動で使われる。
3. 更新直前の状態に**完全に**戻したい場合は、VeloX を終了した状態で
   `<name>.v<旧版>.bak` を `<name>` へコピーする。

### 3.2 もう一度新版へ上げる

新版で書かれていたデータは `<name>.v<新版>.bak` に残っている。旧版で使っていた
間の変更が要らなければ、VeloX を終了した状態でそれを `<name>` へコピーしてから
新版を起動する。コピーしなければ、旧版が書いたファイルが通常どおり新版へ移行
される。

### 3.3 壊れたファイルを調べる・戻す

`<name>.corrupt-<unixミリ秒>` は退避した元のバイト列そのもの。手で直せる場合は
直して `<name>` へコピーすれば次回起動で読まれる。

`browser::migration::restore_backup` が 3.1 の手順 3 と同じ操作 (置き換える前の
ファイルもその版の `.bak` として控える) を提供している。UI からの呼び出しはまだ
無い (将来課題)。

## 4. 構造を変えるとき (開発者向け手順)

**追加だけの変更 (`#[serde(default)]` 付きのフィールド追加) なら版は上げない。**
旧版は未知のフィールドを無視して読めるので、ロールバックもそのまま効く。

フィールドの削除・改名・型変更・意味の変更は構造変更で、次の手順を踏む:

1. 該当ストアの版の定数を 1 上げる (設定以外のストアの版を個別に変える場合は、
   `persistence::schema_for` でそのファイルだけ別の定数を返すようにする)。
2. `migration::Migration { from: 旧版, run }` を登録する。`run` は
   `serde_json::Value → Result<Value, String>` の純粋関数で、**旧版の形だけを
   前提に書く** (現在の Rust の型を経由しない — 型は将来また変わる)。失敗は
   `Err` で返し、パニックしない。
3. 既に登録済みの移行は**消さない・書き換えない**。古い版から現在の版まで
   1 版ずつ辿れることが前提 (途中が欠けると `MigrationFailed` になる)。
4. 旧版のファイルを入力にした単体テストを `persistence.rs` に足す (移行結果と、
   `.v<旧版>.bak` が元のバイト列であること)。
5. Release 本文に「この版は `<name>` の構造を変える。旧版へ戻すと §3.1 の
   手順 2 の動作になる」ことを書く ([release-channels.md](release-channels.md) §6.3)。

`schema_version` 欄の無いファイルは `Schema::legacy_version` の版として読む。
今ある全ストアは「欄なし = 版 1」で、ここを変えると既存プロファイルの読み方が
変わるので変えない。

## 5. 見送ったもの

- 控え (`.v<N>.bak`) の世代管理はしない (版ごとに最新 1 つ)。版が上がるのは稀で、
  同じ版から何度も移行することは無いため。
- 起動時の通知 UI (「データを移行しました」「壊れたファイルを退避しました」) は
  無い。stderr のログのみ。
- ダウングレード後に旧版が保存すると、ファイル自体は旧版の形で上書きされる
  (新版のデータは `.v<新版>.bak` にだけ残る)。起動を拒否する方式 (Chrome の
  「プロファイルが新しすぎる」) は、1 名体制でロールバック手段を利用者に残す
  ことを優先して採らなかった (D164)。
