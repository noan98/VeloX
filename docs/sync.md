# 複数端末同期のアーキテクチャ (Issue #85 / Epic #80)

VeloX の同期の**設計仕様**です。実装は `src/browser/sync/` にある純粋ロジック
(アプリ本体には未接続、挙動の変更なし) で、この文書の各節とモジュールが
1 対 1 に対応します。判断の経緯は
[decisions/archive.md の D160](decisions/archive.md) を参照してください。

**現時点で存在しないもの**: 同期サーバ、アカウント、E2E 暗号化と鍵管理
(#86、オーナー判断待ち)、UI、設定項目、`app.rs` との接続。詳しくは §12。

## 1. 目標と非目標

目標: ブックマーク・設定・(オプトインで) 履歴を複数端末で揃える。オフラインでも
使え、復帰したら収束する。どのサーバ実装・暗号化方式とも組み合わせられる。

非目標: リアルタイム共同編集、サーバ側での内容検索・変換 (サーバは内容を
読めない前提 = E2E)、端末間のタブ転送 (§2 の「後で」)。

## 2. 同期対象

| ストア | 判断 | 理由 |
| --- | --- | --- |
| ブックマーク (`bookmarks`) + フォルダ | **同期する** | 端末をまたいで価値が最も高く、データ量が小さい。フォルダは 1 階層 (D32) なのでツリー移動の競合が「`folder` フィールドの LWW」に縮む |
| 設定 (`settings`) の `general` / `appearance` / `search` / `privacy` | **同期する** (キー単位) | 好みは端末をまたいで共通。許可リスト方式 (`SYNCED_SETTING_GROUPS`) |
| 設定の `performance` / `downloads` / `advanced` | **同期しない** | RAM/CPU 依存の閾値、保存先パス、端末固有の診断値。同期すると別端末で壊れる/悪用される |
| 閲覧履歴 (`history`) | **同期する — ただし既定オフ (オプトイン)** | URL の羅列は最も機微。E2E (#86) が入るまで出さない。追記中心で競合は和集合になるので技術的には容易 |
| セッション/ワークスペース (`session`) | **後で** | 開いているタブは端末ごとに意味が違い、上書き同期は事故になる。将来は「他の端末のタブ一覧 (読み取り専用)」として別種別で足す |
| 入力履歴 (`input_history`、検索語) | **同期しない (当面)** | 検索語は URL より個人的。必要性も低い |
| サイト権限 (`site_permissions`) | **同期しない** | カメラ/位置情報の許可を他端末へ黙って広げるのは安全側に反する |
| ダウンロード、サイトデータ (Cookie 等)、フィルタリスト、ベンチ/計測ログ | **同期しない** | 端末固有・巨大・またはセキュリティ上の理由 |
| **プライベートモード** | **絶対に同期しない** | `SyncScope::accepts` が種別設定より先に判定する。ローカルの変更が同期キューに入る前の唯一の関門なので、ここで落とせば送信・保存のどこにも残らない |

コード上の同期種別は `Kind` = `Bookmark` / `BookmarkFolder` / `Setting` /
`History` の 4 つだけ。ここに無いものは型として存在しないので、うっかり同期する
ことがない。

## 3. 端末 ID と認証境界

- **端末 ID** (`DeviceId`): `[A-Za-z0-9_-]{1,64}`。初回に端末が乱数で採番し
  ローカルに保存する (採番自体は呼び出し側)。HLC の最終タイブレークと、自分の
  書き込みのエコー除外に使う。**名乗りにすぎず、認証には使わない**。
- **認証境界**: この層が扱うのは「復号済みのエンベロープ」だけ。誰が書いて
  よいか (認証・認可)、内容の機密性・改竄検出 (E2E 暗号化・鍵管理・端末の
  追加/失効) は**すべて `Transport` の向こう側 = #86 の責務**。
- `Transport` trait は 2 操作だけを要求する: `push(payload)` (サーバの追記
  専用ログに積む。`Ok` = 永続化済み)、`pull(after: Cursor, limit)` (カーソル
  より後のペイロードを返す)。サーバは不透明なバイト列と単調増加のカーソルしか
  知らなくてよく、HTTP でもファイル共有でも実装できる。

## 4. 論理時計: ハイブリッド論理時計 (HLC) を採用

比較した案:

| 案 | 評価 |
| --- | --- |
| 壁時計のみ (LWW) | 端末の時計ずれ・巻き戻しで「古い編集が新しい編集に勝つ」。却下 |
| バージョンベクトル | 真の並行検出ができるが、端末数に比例して各レコードが肥大し、端末の追加/失効でベクトルの管理が要る。本件の競合解決はフィールド単位 LWW で足りるので過剰 |
| **HLC** | 1 値 `(wall, counter, device)` で全順序。壁時計に近く (人間が見て自然)、因果順序を保つ (受信した書き込みの後の書き込みは必ず大きい)。サイズ一定 |

- `HlcClock::tick(now)`: 巻き戻っても単調増加。`observe(remote, now)`: リモートの
  値を見て時計を進める。時刻は**引数で注入**するので決定的にテストできる。
- **時計の暴走対策**: リモートの `wall` が現在時刻より 24 時間 (`MAX_CLOCK_DRIFT_MS`)
  以上先なら拒否する (1 台の壊れた端末が時計を未来へ固定して以後の全編集に
  勝ち続けるのを防ぐ)。拒否したレコードは適用せず `rejected` に数える。
- 端末 ID がタイブレークなので、別々の書き込みが同じ HLC になることはない。

## 5. データモデル

### 5.1 レコード

`Record { key: (Kind, id), fields: name -> {hlc, value}, tombstone: Option<Hlc> }`。

- `id` は作成端末が採番する不透明な文字列 (端末 ID + HLC などで衝突しない
  ように)。**ローカルの連番 `u64` はそのまま使わない** (端末間で衝突する)。
- **フィールド単位の LWW レジスタ**: フィールドごとに「値 + 書いた時点の HLC」。
  別々のフィールドへの同時編集は両方生き残る (端末 A がタイトル、B がフォルダ
  を変えたら両方反映)。
- **墓石**: 削除は `tombstone = HLC`。墓石以前のフィールドは無効 (刈り取る)。
  **墓石より後に書かれたフィールドは復活させる** (「後の編集は先の削除に勝つ」)。
  削除が後なら削除が勝つ。

### 5.2 結合 (`Record::merge`)

フィールドごとに HLC が大きい方を採り、墓石は max、最後に墓石以前のフィールドを
刈り取る。**交換則・結合則・冪等則**を満たす (総当たりのテストあり)。したがって

- 配送順序が入れ替わっても、
- 同じものが何度届いても、
- 途中の一部が遅れて届いても

最終状態は同じになる。**レコード = デルタ = 状態**なので、線上のペイロード、
送信キューの要素 (畳み込みは `merge` そのもの)、端末内の状態が同じ型で済む。
(同一 HLC で値が違う不正な入力も、値の JSON 表現の辞書順で決めて収束を保つ。)

### 5.3 収束するもの / しないもの

収束保証があるのは `SyncState` (レコードの集合) だけ。意味的な整合
(URL 重複、壊れた `folder` 参照) は**ビューが毎回決定的に解決**し、状態は
書き換えない (§6)。どの端末でも同じ入力から同じ見え方になる。

### 5.4 墓石の回収

墓石は永久には持てない。`SyncState::compact(before_wall)` が古い墓石を捨てるが、
**全端末がその墓石を受け取った後でなければ安全でない** (古い端末が復帰すると
削除が巻き戻る)。安全条件 (サーバが持つ全端末の最小 ack カーソル) の判定は
サーバ設計 (#86 以降) の課題で、当面は呼び出さない。

## 6. 競合解決方針 (データ種別ごと)

| データ | 方針 |
| --- | --- |
| ブックマーク | フィールド単位 LWW (`url`/`title`/`folder`/`order`/`created_at`)。**同じ URL は 1 件にまとめる** (ローカルストアが URL で重複排除する D32 と揃え、勝者は `(created_at, id)` 最小。敗者は隠れるだけで、勝者が削除されれば次が出る) |
| ブックマークの並び | 手動並べ替え (D34) は `order` (整数) の LWW。同順位は `id` で決定的に並べる。並べ替えの中間挿入は呼び出し側が疎な値を振る前提 (フラクショナルインデックスは後で) |
| フォルダ移動 | `folder` フィールドの LWW (1 階層なのでツリーの循環は起きない)。**削除済み/存在しないフォルダを指す場合はルートに落とす** (D62 の `folder_id` 自己修復と同じ。ブックマークは失われない) |
| フォルダ削除 | 墓石。中のブックマークはビューでルートへ (連鎖削除しない — 同時に別端末が中に追加していても失われない) |
| 設定 | **キー単位** (`group.key` = レコード ID、値は `value` フィールド) の LWW。許可リスト外のキーはリモートが送っても**ビューに出さない** |
| 履歴 | 訪問は追記のみ・端末が採番した ID なので衝突せず**和集合**。タイトル/favicon は後から入る LWW フィールド。削除は墓石 (履歴削除 UI の意図が優先) |
| 削除 vs 編集 | HLC で決める: 削除が後なら削除、編集が後なら復活 (§5.1) |

「サイレントに勝敗が決まる」のが不満な場面 (同一フィールドの同時編集) は
Last-Writer-Wins の仕様として受け入れる。ユーザ向けの競合通知は非目標。

## 7. 増分同期・オフラインキュー・復帰

### 7.1 増分同期

サーバは追記専用ログと単調増加の**カーソル**を持つ。端末は最後に処理した
カーソルを保存し、`pull(after)` で差分だけ受け取る。自分が出したエンベロープは
端末 ID で識別してスキップ (適用しても冪等なので害はない)。カーソル 0 から
読めば新規端末が全量を取得できる (墓石込み)。カーソルは**ペイロードを処理し
終えてから**進める (未対応版で止まった時に取りこぼさない)。

### 7.2 送信キュー (`OutboundQueue`)

- **畳み込み**: 同じレコードへの変更は `merge` で 1 件に。オフライン中に何度
  編集しても送るのは 1 件。送信中に追加された編集は ack で消えず残る。
- **上限つき** (既定 1024 レコード)。溢れたらキューを捨てて
  `needs_full_resync` を立て、次の同期でローカル状態の**全量を送り直す**。
  状態ベースなのでキューは「送る候補の索引」にすぎず、変更を黙って失わない。
- **at-least-once**: バッチを送って `ack` で消す。失敗は `nack` で指数
  バックオフ (1s → 上限 60s、ジッタは呼び出し側が足す)。ack が失われても再送
  されるが結合は冪等。直列送信 (飛行中のバッチは 1 つ)。
- **再起動を跨ぐ**: キューは `Serialize`/`Deserialize` でき、読み戻すと飛行中
  だったバッチは未送信に戻る。時計 (`HlcClock::last` / `restore`) とカーソルも
  永続化して復元する (単調性を保つ)。

### 7.3 オフラインからの復帰

1. オフライン中: ローカル編集は状態に即反映し、キューに畳み込んで貯める
   (同期は失敗 `Offline` を返すだけで何も失わない)。
2. 復帰: バックオフが明けたら `sync` が push → pull の順に 1 往復。
3. 双方が編集していても、結合則により順序に依らず同一状態に収束する
   (テスト: 2 台のオフライン同時編集、3 台の全配送順序 720 通り、ack ロスト、
   キュー溢れ、途中参加端末)。

## 8. ペイロードとプロトコルバージョン

```json
{ "v": 1, "device": "laptop-3f9a", "records": [
  { "key": {"kind": "bookmark", "id": "…"},
    "fields": {"url": {"hlc": {"wall": 1750000000000, "counter": 0, "device": "…"}, "value": "https://…"}},
    "tombstone": null } ] }
```

- 整数 `v` (`PROTOCOL_VERSION` = 1、読める最古は `MIN_PROTOCOL_VERSION` = 1)。
- **同じ版の中ではフィールドの追加だけ**を許す (未知フィールドは無視して読める)。
  意味が変わる変更 (競合解決の変更、フィールドの意味変更など) だけ `v` を上げる。
- **交渉** (`negotiate`): 双方の `[min, max]` から共通の最大版を選ぶ。無ければ
  「こちらが古い (更新を促す)」/「相手が古い (待つ)」を区別して返す。
- **受信時**: `v` を**先に**見る。範囲外なら `UpgradeRequired(v)` を返して
  適用も**カーソルを進めることもしない** (更新後にやり直せば取りこぼさない)。
  壊れた/検証に落ちたペイロードは `rejected` に数えて飛ばす。
- **サイズ上限**: エンベロープ 4 MiB、1 通 1000 レコード、ID 256 バイト、1 レコード
  32 フィールド、1 値 16 KiB。リモート入力は必ず `validate` を通す。
- **マイグレーション方針**: `v` を上げる時は、新旧を読める期間 (`min` を据え置き)
  を設け、古い端末には更新を促す。ローカル保存物 (キュー) は serde の
  `#[serde(default)]` で前方互換を保つ (settings と同じ流儀)。
  この文書の §8 と `protocol.rs` を同じ PR で更新する。

## 9. 脅威モデル (基本)

前提: サーバ/経路は信用しない。他端末も、鍵が漏れれば悪意を持ちうる。

| 脅威 | この層の対策 | 残る課題 (#86 など) |
| --- | --- | --- |
| サーバ/経路による盗聴 | なし (平文エンベロープ) | **E2E 暗号化は #86。それまで実サーバに接続しない** |
| 改竄・なりすまし | なし | #86 の認証つき暗号 |
| 悪意ある/壊れた端末が巨大・不正データを送る | サイズ・個数の検証、未知の版の拒否 | — |
| 時計を未来へ固定して以後の編集に勝つ | 24 時間超の先行は拒否 (§4) | 上限内の先行は許容 |
| 悪意ある設定の書き換え (保存先パス等) | 許可リストに無いキーは無視 | — |
| 悪意ある URL (`javascript:` 等) の混入 | この層は URL を解釈しない。**適用側 (将来の接続層) が既存のスキーム許可リスト (D62) を必ず通す** | 接続時に必須 |
| 削除の巻き戻し (リプレイ) | 墓石は max で結合され、HLC の大きい書き込みだけが勝つ | 墓石回収の安全条件 (§5.4) |
| プライバシー (履歴の流出) | プライベートモードは常に除外、履歴は既定オフ (§2) | 暗号化前提 |
| DoS (キューの肥大) | 上限つき + 全量再送 | — |

## 10. テスト

`src/browser/sync/*` のユニットテスト (`cargo test sync`): HLC の単調性・
ドリフト拒否、`merge` の交換/結合/冪等の総当たり、種別ごとのビュー、キューの
畳み込み・上限・ack/nack・再起動、プロトコルの版交渉・検証、そして
`Replica` + インメモリのフェイクサーバによる複数端末の収束シナリオ。
