# リリースチャネルとリリースポリシー

Issue #88 / Epic #81。Nightly / Beta / Stable の目的・バージョニング・Stable 昇格
条件・ロールバック方針を定める**方針文書**である。設計判断の記録は
[docs/decisions.md](decisions.md) の **D161** を参照。

> **位置付け**: 本書は「何をリリースと呼び、何を満たせば Stable と呼ぶか」を決める。
> 実際のリリース手順書 (タグを打つ・Release を確認する等) は別 PR
> (PR 予定の手順書) が扱う。自動更新 (#90)・パッケージング (#91)・移行/ロールバック
> (#92) は本書の**前提ではなく依存先**で、未実装の間は下記「現状の制約」に従う。

## 1. 現状の制約 (方針の前提)

| 項目 | 現状 | 方針への影響 |
| --- | --- | --- |
| 配布 | GitHub Release に Windows インストーラ (`*-setup.exe`) と Linux `tar.gz` を添付 (`release-windows.yml` / `release-linux.yml`)。macOS は配布物なし | 配布経路は GitHub Release 1 本。Windows を最優先 (CLAUDE.md) |
| 自動更新 | **無い** (#90 未実装) | ユーザは手動で再インストールする。「チャネルを切り替える」機能は無く、チャネル = 「どの Release を手で取るか」 |
| コード署名 | Secrets 未設定なら**無署名**でビルド継続 (D73、`docs/windows-code-signing.md`) | SmartScreen 警告が出うる。Stable でも署名の有無を Release 本文が明記する (既存動作) |
| データ移行 | **未実装** (#92)。設定は `schema_version = 1` (`src/browser/settings.rs`)。追加フィールドのみ許容 (古い版が新しい版の設定を読んでも未知フィールドは無視される) | ダウングレードの安全性は「スキーマを壊さない」規律に依存する (§6) |
| 体制 | 個人メンテナ 1 名 | チャネル数と運用負荷を絞る (§2) |

## 2. チャネル

**3 チャネルのうち、運用として実在させるのは 2 つ (Beta / Stable)。Nightly は
「タグを打たない成果物」に留める。** 個人メンテナが 3 種類の Release を継続的に
手で維持するのは現実的でなく、かつ自動更新が無いので細かいチャネル分けの利点
(段階配布・自動追従) が得られないためである。

| チャネル | 目的 | 想定利用者 | 頻度 | 成果物の所在 | 保証 |
| --- | --- | --- | --- | --- | --- |
| **Nightly** | `main` の最新を動かして早期に壊れ方を見る | メンテナ本人・開発協力者 | 必要なとき (手動)。定時ビルドは**作らない** (§7) | `release-windows.yml` / `release-linux.yml` を `workflow_dispatch` で実行して得る Actions Artifact (保持 30 日)。**GitHub Release にもタグにもしない** | なし。CI が緑の `main` であることのみ |
| **Beta** | Stable 候補の実機確認・ソーク (§5) | 先行して試したい利用者 | Stable の前に 1 回以上。目安として 2〜4 週間に 1 回まで | GitHub Release (**pre-release 印付き**)、タグ `vX.Y.Z-beta.N` | 昇格条件のうち機械判定可能なゲートを通過済み。設定/履歴の互換は保つが、不具合は想定内 |
| **Stable** | 一般利用者に勧める版 | 全利用者 | Beta のソークを通過したとき。固定周期は設けない | GitHub Release (pre-release 印なし)、タグ `vX.Y.Z` | §5 の昇格条件をすべて満たす。既知の重大不具合なし |

- 頻度を固定周期にしないのは、個人メンテナが周期を守るために品質ゲートを緩める
  誘因を避けるため。**周期より昇格条件を優先する。**
- 利用者数と体制が増え、自動更新 (#90) が入った時点で、Nightly を定時ビルド +
  Release 化する拡張を再検討する (§9)。

## 3. バージョニング

**SemVer 2.0.0** に従う。ただし `1.0.0` 未満の間は次の読み替えを採る:

- `0.MINOR.PATCH`: `MINOR` を上げるのは機能追加・挙動変更・**永続データの形式追加**。
  `PATCH` は不具合修正のみで、永続データの形式・設定の意味を変えない。
- `1.0.0` は「§5 を満たし、#92 (移行/ロールバック) が実装され、自動更新 (#90) が
  ある」ことを目安とする。日付や機能数では決めない。

### タグと `Cargo.toml` の関係

| チャネル | タグ | `Cargo.toml` の `version` | 例 |
| --- | --- | --- | --- |
| Stable | `vX.Y.Z` | `X.Y.Z` | `v0.2.0` |
| Beta | `vX.Y.Z-beta.N` (`N` は 1 始まり) | `X.Y.Z-beta.N` | `v0.2.0-beta.1` |
| Nightly | **タグなし** | 変更しない (`X.Y.Z`) | ファイル名は `Actions の実行 ID / コミット SHA` で識別 |

- **タグは `Cargo.toml` の `version` と完全一致させる**。`release-windows.yml` が
  `v` を除いたタグと `cargo metadata` の version を比較し、不一致ならビルドを
  失敗させる (既存の検査)。したがって Beta を出すには、`Cargo.toml` を
  `X.Y.Z-beta.N` にした commit にタグを打つ。Stable にするときは `Cargo.toml` を
  `X.Y.Z` に戻した**新しい commit** にタグを打つ (Beta のタグを付け替えない)。
- インストーラ名は `velox-<version>-windows-x86_64-setup.exe` で、`version` は
  `Cargo.toml` から取る。SemVer の pre-release 識別子 (`-beta.1`) はそのまま
  ファイル名に載るので Beta と Stable は名前で区別できる。
- **pre-release 識別子は `beta.N` のみ使う。** `alpha` / `rc` は増やさない
  (チャネルが 2 つしか実在しないため)。SemVer 上 `0.2.0-beta.2 < 0.2.0` なので
  優先順位は自然に正しい。
- pre-release を含むタグ (`-` を含む) は GitHub 上で **pre-release として公開**
  する。これは `release-windows.yml` / `release-linux.yml` が自動で行う (§7)。
  「最新 (Latest)」は Stable のみが取る。
- `Cargo.lock` は `--locked` でビルドされるため、`version` を変えたら `Cargo.lock`
  も同じ commit で更新する。

## 4. Stable 昇格の考え方

昇格 = 「Beta `vX.Y.Z-beta.N` と同一内容で `vX.Y.Z` を出すこと」。コードを変えて
から昇格してはならない。変更が要るなら `beta.N+1` を切り、ソークをやり直す。
(差分は `Cargo.toml`/`Cargo.lock` の version 行のみとし、PR でそれを確認する。)

## 5. Stable 昇格条件

すべて満たすこと。**機械判定** はリポジトリの既存ゲートで確認でき、**手動判定** は
メンテナが Release の記録 (Issue コメントなど) に残す。

### 5.1 ビルド・テスト (機械判定)

1. 昇格元 commit の CI (`ci.yml`) が **Linux / Windows の両ジョブとも success**
   (fmt・clippy・test・build。Windows は build・clippy・`--lib` test。Windows の
   統合テストは D61 により対象外である点を了承した上で判断する)。
2. `release-windows.yml` がそのタグで成功し、インストーラが生成されている
   (サイズ検査・署名検証は workflow が実施)。`release-linux.yml` も成功している
   (Linux は「ビルドが通る」ことのみが条件で、CLAUDE.md の優先度方針どおり)。
3. `dependency-audit.yml` / `codeql.yml` に**未対応の high 以上の指摘がない**。

### 5.2 性能 (機械判定 + 手動)

`docs/performance-targets.md` の目標と、既存ゲートの閾値に従う。**これらのゲートが
判定するのは「直前との相対回帰」であり、絶対値の合否ではない**点に注意する。

1. PR 単位の `perf-gate.yml` (Linux) が、Beta までの変更で **fail (回帰 60% 超) に
   なっていない**。warn (20% 超) は理由を説明できること (`GateThresholds` の既定値)。
2. `perf-windows.yml` (Windows。手動 + 週次。**PR ゲートではない**) を、Beta の commit
   に対して `workflow_dispatch` で 1 回実行し、直近の実行と比べて大きな悪化がない
   ことを確認する。Windows の数値を Linux の実力値と混ぜない (Epic #57 の原則)。
3. メモリ予算の判定 (`VELOX_MEMORY_BUDGET_INPUT` の既定は D152 により Windows で
   private) が既存の予算内。

> 性能ゲートは現時点で Stable の**ブロッカーではなく、根拠付きの確認項目**として
> 使う。`perf-windows.yml` は実行環境の個体差が大きい (D96) ため、単一の run の
> 数値でブロックしない。悪化が疑われるときは `compare_env` の同一ジョブ A/B で切り
> 分けてから判断する。

### 5.3 不具合 (手動判定)

- Beta 公開後に報告された Issue のうち、**データ損失・起動不能・クラッシュ・
  セキュリティ**に該当するものが 0 件 (open)。
- 上記に該当しない既知の不具合は、Release 本文の「既知の問題」に記載すれば残して
  よい。
- 該当ラベルは現時点で未整備。運用に入る際に `release-blocker` ラベルを新設し、
  open が 0 であることを条件にする (§9)。

### 5.4 ソーク (手動判定)

- Beta 公開から **最低 7 日** (Windows 実機で日常利用) 経過している。メンテナ自身が
  Beta を常用し、**再起動をまたいだセッション復元・履歴・ブックマーク・設定の保持**
  を確認する。
- 前の Stable からの**アップグレード**を実機で 1 回確認する (旧版の上に新版をインス
  トールして、データが残ること)。
- この期間に新しい Beta (`beta.N+1`) を切ったら、経過日数は数え直す。

### 5.5 データ互換 (手動判定)

- 前の Stable と比べて、設定 (`schema_version`)・セッション・履歴・ブックマークなど
  **永続データの形式が変わっていない、または追加のみ**である (§6.3)。
- 形式を壊す変更を含む場合は、#92 (移行) が入るまで Stable にしない。

## 6. ロールバック方針

**前提: 自動更新 (#90) も移行 (#92) も無い。** ロールバックとは「利用者に古い
安定版を再び勧める」ことであり、利用者側のダウングレードは手動再インストール
である。

### 6.1 レベルと対応

| 状況 | 対応 | 時間の目安 |
| --- | --- | --- |
| Beta に不具合 | Release を取り下げず、次の `beta.N+1` で修正する。深刻なら Release 本文の冒頭に警告を追記 | 随時 |
| Stable に重大な不具合 (データ損失・起動不能・セキュリティ) | ① Release 本文の冒頭に**警告と回避策** ② 問題の Release を **pre-release に戻す**、または Draft に戻して一般の目に触れなくする ③ 直前の Stable (`vX.Y.Z-1`) を **Latest に戻す** ④ 修正版を `vX.Y.(Z+1)` として出す (§5 を短縮せずに通す。ただしソークは Beta ではなくメンテナ実機の再現確認で足りる場合のみ 3 日まで) | 判明後できるだけ早く |
| 軽微な不具合 | 通常どおり次の PATCH で直す | — |

### 6.2 やってはいけないこと

- **タグの付け替え・削除、Release の作り直し (force push でタグを動かす等) をしない。**
  既に配布されたバイナリと履歴が食い違い、原因調査ができなくなる。誤ったリリースは
  **新しい版番号で上書き**する (PATCH を進める)。
- **バージョン番号を戻さない。** 「0.2.1 を出して 0.2.0 の内容に戻す」のように、
  内容を戻すときも番号は進める (Cargo の SemVer 順と、将来の自動更新の判定を守る)。
- crates.io へは公開していないので `cargo yank` は対象外。ここでの「yank」は
  上記 ② (Release を pre-release / Draft に戻す) を指す。

### 6.3 データ互換 (ダウングレードのリスク)

#92 が未実装のため、**新版が書いたデータを旧版が読めることは保証されない**。
そこで Stable にする版には次の規律を課す:

- 永続データの形式変更は **追加のみ** (新規フィールドは `#[serde(default)]`、
  既存フィールドの意味・型を変えない)。設定は `deny_unknown_fields` を付けない
  現在の実装により、旧版が新版の追加フィールドを無視して読める。
- **構造変更 (フィールドの削除・型変更・ファイル形式の変更) は `schema_version` を
  上げる**。この種の変更を含む版は、#92 が入るまでは Stable にしない
  (Beta 止まり)。含む場合は Release 本文に「旧版へ戻せない」ことを明記する。
- 上記を守れなかった版をロールバックする場合は、Release 本文で「設定ファイルを
  退避して旧版を入れ直す」手順 (データの場所は利用者向けガイドを参照) を案内し、
  データが失われうることを隠さない。
- ロールバックの対象になった不具合が「データ形式の破損」だった場合は、修正版に
  そのデータを読める救済処理を入れるか、#92 の課題として起票する。

## 7. 自動 / 手動の区分

| 作業 | 区分 | 備考 |
| --- | --- | --- |
| タグ push でのビルドと Release への添付 | **自動** | 既存 (`release-*.yml`) |
| タグと `Cargo.toml` の version 一致検査 | **自動** | 既存 (Windows workflow) |
| `-` を含むタグを pre-release として公開 | **自動** | D161 で両 workflow に追加 (`prerelease` に `contains(github.ref_name, '-')` を渡すだけ。新しい trigger・権限・Secrets は無い) |
| Nightly 成果物 | **手動** (`workflow_dispatch`) | 定時実行は作らない |
| `Cargo.toml` の version 更新・タグ打ち | **手動** | メンテナが実施。手順書は別 PR |
| §5 の昇格判定 | **手動** | ゲートの結果を人が読んで決める。自動昇格は作らない |
| Stable への「昇格操作」 | **手動** | `vX.Y.Z` を打つ = 昇格 |
| 「Latest」の付け替え・pre-release 戻し | **手動** | GitHub の UI / `gh release edit` |
| 利用者への通知 | **手動** | 自動更新が無いので Release と README のみ |

昇格判定を自動化しない理由: ① 性能ゲートの一部 (`perf-windows.yml`) は個体差が
大きく PR ゲートにできていない (D96/#211)、② 体制が 1 名で判定を人が握るほうが
安全、③ 公開リポジトリで write 権限を持つ workflow を増やすほど攻撃面
(CLAUDE.md の trigger ガード) が増える。

## 9. 将来課題 (本 PR では実施しない)

- `release-blocker` ラベルの新設と、open が 0 であることの機械チェック。
- Nightly の定時ビルドと Release 化 (自動更新が入り、利用者が増えてから)。
- タグ形式の検査 (`vX.Y.Z` または `vX.Y.Z-beta.N` 以外を弾く) を workflow に入れる。
  正規表現が明確に決められるが、既存タグ運用への影響を確認してから行う。
- 昇格条件のチェックリスト自動生成 (直近の CI / perf 結果を Release 下書きに貼る)。
- macOS の配布物 (CLAUDE.md の優先度方針により品質確立後)。
